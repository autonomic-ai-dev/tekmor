# tekmor harness

Measures whether tekmor changes the outcome of a coding task, against the same task run without it.

## Pre-registration

Question: with tekmor's gates and proof in place, does an agent's change pass an independent acceptance test more often, and at what cost in turns and dollars?

Primary metric: `accepted`, whether the hidden acceptance script passes on the final repo.

Secondary metrics, recorded per run:
- `turns` and `duration_ms` from the CLI result;
- `cost_usd` from the CLI result;
- `stop_events`, the number of gate events mentioning `stop` in the run's gate log;
- `receipt`, the first line of `tekmor verify receipt` for the final tree.

Arms:
- `control`: the fixture repo, no tekmor.
- `tekmor`: the same fixture plus a feature map, a knowledge-base entry, an allowlist with the visible check, and the project-level gate hooks installed by `tekmor install`.

Both arms get the same prompt and the same fixture. The acceptance script is never shown to the agent and is run from outside the repo.

Design: paired by task and repetition. Each task runs `REPS` times in each arm.

Analysis: per task, the difference in acceptance rate between arms, with a bootstrap interval over repetitions. Cost and turns are reported as medians with the sample size. Nothing is reported as a win without its interval and `n`.

Budget: each run is capped with `BUDGET_USD` (default 1). The total is the cap times the number of runs.

## Tasks

- `clamp`: a bounds function returns the wrong bound. Visible check: three cases. Acceptance: seven cases.
- `slug`: a slug function lowercases but does not normalise separators. Visible check: two cases. Acceptance: five cases.

Both fixtures fail their checks before the fix, and both acceptance scripts pass with a correct fix.

These two are toy tasks. They check that the harness works. They are not evidence about your work. Add tasks taken from your own repositories before drawing a conclusion.

## Running

```
cargo build -p tekmor
python3 bench/build_tasks.py && python3 bench/validate_tasks.py   # 50 of 50 must be valid
DRY_RUN=1 RESULTS_DIR=results/dry REPS=1 ./run_matrix.sh          # setup for every task, no model call
RESULTS_DIR=results/bench-v1 REPS=10 PAR=4 CEILING_USD=60 ./run_matrix.sh   # the full benchmark
python3 analyze.py results/bench-v1                               # the pre-registered analysis
```

Single runs: `./run.sh b44_prime control 1` (needs the claude CLI and an API key).

Real runs use `--permission-mode bypassPermissions` inside a temporary repo. Each run is deleted when it ends.

Results go to `harness/results/` and are not committed.

## Amendments

- The prompts of both tasks gained one closing sentence, the same in both arms: run `sh check.sh` and state its output. The earlier pilot used the old prompts and is not comparable, so its rows are removed from the analysis.

- Runs load only project and local settings (`--setting-sources project,local`), so a user's global hooks do not reach the agent. The user's global instruction files still load, in both arms alike. An empty config directory fails to authenticate, so they cannot be removed without copying credentials.

## Benchmark v1: 50 tasks

Written and fixed before any run of this benchmark.

Tasks: `tasks/b01_*` to `tasks/b50_*`, generated by `bench/build_tasks.py` from `bench/specs.py`. Each is one Python module with one injected bug, written as an issue report. The agent sees `fixture/` and the visible check `check.py` (run through `sh check.sh`). The hidden acceptance cases are in `hidden.py`, outside the repo, and run through `accept.sh`. Expected values come from running the reference module. These are synthetic bugs, not bugs from real repositories, so they measure whether the agent finishes a stated fix, not performance on real code.

Validity gate: `bench/validate_tasks.py` must report 50 of 50 valid before a run. The buggy fixture must fail both checks, and the reference fix must pass both. Two tasks failed this check during construction, because their hidden cases missed the bug. Boundary cases were added, which is why the specs changed after the first build. The loader also disables bytecode caching: a stale `.pyc` with the same size and mtime second served buggy code to the reference fix in validation.

Design: 50 tasks, both arms, 10 repetitions per task per arm, 1000 runs. The matrix runs rep by rep, so stopping early still leaves every task paired. Same prompts and fixtures in both arms. Settings as in the amendments above.

Budget: each run is capped at `BUDGET_USD` (default $1). The matrix stops before a repetition if the recorded total has reached `CEILING_USD` (default $60). The pilot cost about $0.005 per control run and $0.016 per tekmor run on one task, so the expected total is about $10.

Primary metric: `accepted`, whether the hidden acceptance script passes on the final repo. Agent errors are counted as attempts and scored by the same hidden script. No runs are excluded.

Effect: for each task, the accepted rate in the tekmor arm minus the control arm. The headline is the mean of those differences across tasks, so each task counts once.

Interval: 95% cluster bootstrap, 5000 resamples, seed 20261117. Each resample draws tasks with replacement, then repetitions within each task and arm.

Decision rule:
- If the lower bound of the interval is above 0, the result is "tekmor improves acceptance at this scale".
- If the upper bound is below 0, the result is "tekmor reduces acceptance at this scale".
- Otherwise the result is "no detectable difference at this sample size". It is not reported as "no effect".

Secondary, reported with no decision attached: PASSED receipts per arm, median turns, median cost, total cost, median stop-gate events, and the ratio of median cost. A median cost ratio above 2.0 is reported as a material cost increase.

The pilot results (`results/clamp`, `results/slug`) are not part of this benchmark and are kept in their own folder.
